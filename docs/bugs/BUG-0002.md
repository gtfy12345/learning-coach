# BUG-0002: Codex CLI 升级导致 Web 模型调用失败

> 模块: cli | 严重度: high | 状态: resolved
> 发现日期: 2026-08-17 | 关联 Commit: `fix(cli): restore Codex exec compatibility (BUG-0002)`
> 关联日志: -

## 1 现象

- 使用 `codex_cli:default` 启动 Web 后，创建学习会话返回 HTTP 503。
- 浏览器只显示安全兜底文案“本次模型运行失败，请检查配置后重试”。
- 服务健康检查与模型配置接口正常，影响范围集中在实际 Codex CLI 模型调用。

## 2 诊断过程

### 假设 1：`.env` 或登录态无效

- 验证方法：检查 `/api/config`、`codex login status`，并用官方 CLI 做最小非交互调用。
- 结果：排除。服务已选择 `codex_cli:default`，ChatGPT 登录会话有效。

### 假设 2：Codex exec 参数已经漂移

- 验证方法：用适配器相同参数调用本机 Codex CLI 0.144.1。
- 结果：确认。CLI 对 `--ask-for-approval` 返回 `unexpected argument`，移除旧参数后普通文本调用成功。

### 假设 3：结构化输出 Schema 不再满足服务端约束

- 验证方法：保留完整 CLI stderr，直接运行诊断 Schema 调用。
- 结果：确认。Structured Outputs 要求所有对象节点显式设置 `additionalProperties: false`。

## 3 根因分析

- `src/learning_coach/cli_models.py` 固定了旧版 `codex exec --ask-for-approval never` 命令契约，而 Codex CLI 0.144.1 已改用配置键表达审批策略。
- 适配器直接写入 Pydantic `model_json_schema()`，没有补齐 Codex Structured Outputs 的严格对象约束。
- 原 fake runner 测试只检查部分参数与枚举，没有断言已废弃参数或严格 Schema，因此未能在官方 CLI 升级后预警。

## 4 修复方案

- 用 `-c 'approval_policy="never"'` 替换失效参数，同时保留 `--sandbox read-only` 与 `--ephemeral`。
- 仅在 Codex 边界递归补齐对象 Schema 的 `additionalProperties: false`，不修改 Pydantic 模型或其他 Provider。
- 扩充普通调用、根对象和嵌套对象 Schema 的离线命令契约测试。
- 未采用降低 sandbox、依赖隐式审批默认值或回退 API Key 的绕过方案。

## 5 验证

- `PYTHONPATH=src .venv/bin/python -m pytest tests/test_cli_models.py -q`：10 项通过。
- `PYTHONPATH=src .venv/bin/python -m pytest -q`：317 项通过。
- `compileall` 与 `git diff --check` 通过。
- 修复后的真实文本适配器调用返回 `OK`。
- 重启 Web 后，`POST /api/sessions` 返回 HTTP 201 并生成结构化诊断题。

## 6 经验教训

- 适配官方 CLI 时，升级客户端必须同时核对命令帮助、配置键和结构化输出约束。
- fake runner 应断言安全关键参数的存在与退役参数的缺失，并覆盖 Provider 对 Schema 的额外限制。
- Web 保持脱敏错误是正确边界，但诊断时需要能在服务端或直连适配器层取得经过清理的可操作错误尾部。
