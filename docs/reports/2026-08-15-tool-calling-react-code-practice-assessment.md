## 2 会话中的主要阻点/痛点

### 2.1 代码主题判定一度被讲解正文关键词误触发

- **证据**：初版判定同时扫描主题与讲解正文，普通主题的讲解只要出现“函数”就可能进入代码实践；集成测试暴露后，判定收紧为只读取用户显式主题。
- **影响**：若未修复，原有文本练习会发生不兼容的交互变化，学习者会意外看到代码输入框。

### 2.2 Word 渲染环境没有自动发现可用中文字体

- **证据**：首次 LibreOffice 渲染缺失中文字符；为渲染进程临时提供系统中文字体后恢复，最终检查完成后已移除临时字体链接。
- **影响**：增加了一轮文档渲染验证，但没有改变最终文章内容或仓库运行时依赖。

### 2.3 尾页强调框造成近乎空白的独立页面

- **证据**：首次排版为 7 页，最后一个强调框单独占据第 7 页；删除重复收束框后稳定为 6 页，并再次完成全部页面检查。
- **影响**：产生一次版式迭代，避免公众号源稿出现明显空白尾页。

## 3 根因归类

- “显式代码主题”的边界在方案文字中存在，但没有一开始就转化为单一真理源判定。
  - **类别**：spec-plan
- 中文字体缺失属于当前文档渲染运行时的环境差异，最终 DOCX 使用标准字体回退且已通过渲染检查。
  - **类别**：无需仓库改动
- 尾页强调框属于一次性 Word 流式排版结果，逐页视觉检查已能稳定发现。
  - **类别**：无需仓库改动

## 4 对流程资产的改进建议

- 后续新增自动分流能力时，把“只读取哪些用户字段”写成验收项，并为正文包含相同关键词的负向样例保留回归测试。
  - **落点**：spec-plan
  - **优先级**：high
- 文档生成继续保留“清理元数据后重新渲染并逐页检查”的最终门禁，不把首次渲染结果视为最终证据。
  - **落点**：documents skill
  - **优先级**：medium
- README 和文章持续明确本地执行器不是强隔离沙箱；若未来面向公网或多用户，再先设计容器、虚拟机或专用判题服务。
  - **落点**：README
  - **优先级**：high

## 5 建议优先级与后续动作

1. 保留“普通主题正文含代码关键词”的兼容性回归测试，防止动态分流范围再次扩大。
2. 在任何公网或多用户部署前，用独立隔离执行服务替换当前本地受限进程；现有纵深限制只适合本地单用户教学演示。
3. 下一阶段进入 LangGraph 状态图进阶时，继续沿用工具预算、重复 Action 检测和外层补救次数三重终止条件。
