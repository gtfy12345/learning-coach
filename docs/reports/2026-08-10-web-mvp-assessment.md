- 本次交付为现有 LangGraph 学习教练增加了可实际使用的本地 Web MVP：用户可输入学习主题、上传一张图片，并在浏览器中完成诊断、讲解、测验、结构化评估、有限补救轮次和学习总结。
- Web 层复用了既有模型工厂、CLI 登录态/API Key 配置和 LangGraph 工作流，没有另建一套学习流程；浏览器配置接口只返回模型标识和图片能力，不返回凭证。

- 运行时验证通过：`/api/health` 返回 `{"status":"ok"}`，`/api/config` 返回已配置的 `codex_cli:default`，主页和静态资源均为 200；页面已在内置浏览器中打开，标题为 `Learning Coach · AI 学习教练`。
- 本次没有创建未进入执行或缺少验证证据的后续计划/清单，不存在孤立跟进文档风险。

## 2 会话中的主要阻点/痛点

### 2.1 “有页面”与“功能可用页面”的验收口径需要二次澄清

- **证据**：用户在提出 “先加个 web mvp” 后进一步强调 “至少要让开发的功能页面可以用起来”。
- **影响**：如果只按展示页理解，会遗漏现有诊断、教学、测验、结构化评估和补救流程的完整交互，造成交付目标偏差。

### 2.2 本地 CLI 登录态与静态托管架构不兼容

- **证据**：当前默认模型为 `codex_cli:default`，模型访问依赖本机已登录的 CLI 进程；浏览器本身不能安全、直接地复用该登录态。
- **影响**：Web MVP 必须同时包含本地 Python API，不能只生成静态页面或直接发布到无本机 CLI 的托管环境；需要明确本地运行边界。

### 2.3 Web 测试客户端依赖发生了上游迁移

- **证据**：Starlette 1.6 的测试客户端提示改用 `httpx2`，开发依赖随后调整为 `httpx2>=2.0,<3.0`，告警消失并完成 47 项测试。
- **影响**：产生一次依赖调整，但未造成设计返工或持续阻塞。

## 3 根因归类

- Web MVP 的行为验收条件没有在实现前形成明确清单。
  - **类别**：spec-plan
  - **说明**：症状是用户补充“页面必须把已开发功能用起来”，根因是 MVP 范围只表达了交付形态，没有同步列出端到端用户旅程。
- 本地登录态模型需要有状态后端这一架构约束没有通用地体现在站点工作流入口中。
  - **类别**：skill
  - **说明**：站点类流程容易默认静态或托管交付，但本项目的模型凭证和进程都在本机；本次已在项目 README 中记录边界，后续可在通用站点技能中增加识别提示。
- `httpx2` 迁移属于当前依赖版本组合的一次性适配。
  - **类别**：no repo change needed
  - **说明**：依赖声明和测试已修正，现有自动化能够防止回归，不需要新增治理流程。

## 4 对流程资产的改进建议

- 在下一份 Web 功能方案或实施计划中加入“能力—页面—接口—测试”映射，至少覆盖现有诊断、讲解、测验、评估、补救和总结节点。
  - **落点**：spec-plan
  - **优先级**：high
- 为涉及本地 CLI/OAuth 登录态的 Web 任务增加架构检查：先判断是否需要本地后端、凭证是否能安全留在服务端、目标托管环境能否运行所需进程，再决定静态站点或全栈交付方式。
  - **落点**：sites-building skill
  - **优先级**：medium
- 继续在 README 中维持“本地单用户、内存会话、重启清空、浏览器不接收密钥”的运行边界；若未来加入部署或多人使用，再先设计持久化和用户认证。
  - **落点**：README
  - **优先级**：medium

## 5 建议优先级与后续动作

1. 下一轮最优先补充 Web 功能的验收矩阵，确保新增模型能力都有对应的可操作页面与自动化测试。
2. 若要从本地 MVP 升级为共享后台，先确定认证、会话持久化和远端可用的模型凭证方案；不要直接把本机 CLI 登录态暴露给浏览器或迁移到无进程能力的静态托管。
3. `httpx2` 依赖迁移已经闭环，可随常规依赖升级观察，不需要单独立项。
